# Plan: Release 1.0.0 under the new coordinates

Status: **draft**.

The plugin now lives under `com.github.mlangc` (group, plugin ID and Java packages; previously `io.morethan.jmhreport`).
This plan prepares release 1.0.0, extends the blackbox tests so they can run against a published plugin (not only a
`flatDir` jar), and uses that to double-check the release after the maintainer has published it.

## Ground rules

- Commit messages follow the root `CLAUDE.md`: a terse single-line subject, and a body that is only a bare
  reference to this plan (`plans/2026-10-06-RELEASE-1.0.0.md`).
- The agent does **not** tag, push, run `publishPlugins` (including to the real portal), or merge to `main`. Everything
  up to step 7 happens on the branch `release-1.0.0`, in its own git worktree (see step 1), never in the main
  checkout. Nothing is merged to `main` before the release is published and double-checked (step 8); steps 6 and 8
  are the maintainer's.
- Anything that can't be verified locally (Plugin Portal rules, credentials) is listed as an open item and not assumed.
- Each step ends with its checks green and, where it changes files, at least one commit. Report check output, don't
  summarise it away.

## Starting point

- `gradle.properties` says `projectVersion = 0.9.6`; the last release was 0.9.6 under the old ID. The new ID has never
  been published.
- `jmh-visualizer.zip` is already the 1.0.0 bundle (`44c7186`). Group, plugin ID and Java packages are already
  `com.github.mlangc`.

## Course change (found in step 4)

`./gradlew publishPlugins --validate-only` fails with "Group id must not start with 'com.github', it should be
replaced with 'io.github'". The portal also requires group and plugin ID to share the top-level namespace; with both
changed, validation succeeds. By decision of the maintainer, group, plugin ID and Java packages are renamed to
`io.github.mlangc` (plugin ID `io.github.mlangc.jmhreport`) on this branch. Wherever this plan says
`com.github.mlangc`, read `io.github.mlangc` from there on.

## Steps

### 1. Migrate to 1.0.0 and `com.github.mlangc`; everything still passes

Create a git worktree with the new branch `release-1.0.0` off `main`, next to the main checkout:
`git worktree add -b release-1.0.0 ../gradle-jmh-report-release-1.0.0 main`. All implementation (steps 1 to 5, and
7 on the same branch) happens there; the plan file itself is committed on this branch as its first commit. It is
untracked in the main checkout at that point: move it into the worktree (`mv`, not copy), so that no untracked copy
is left in the main checkout, where it would make the `--ff-only` merge in step 8 fail.
Confirm the worktree is clean and the tool chain works (`mise install`, `./gradlew --version` shows 8.0.2 on
JDK 8). The worktree and the branch stay until the maintainer has merged in step 8; then remove the worktree
(`git worktree remove`) and delete the branch.

- `gradle.properties`: `projectVersion = 1.0.0`.
- Grep the repository for leftovers of the old coordinates (`io.morethan`) and of `0.9.`; fix or consciously keep each
  hit (the News history legitimately mentions old versions). Docs are step 2; code, build files, fixtures and scripts
  are this step.
- Checks: `./gradlew clean jar test`; blackbox check on all Gradle versions with the new jar name:
  `cd blackbox-tests && uv run check.py --jar ../build/libs/gradle-jmh-report-1.0.0.jar`, plus `ruff check`,
  `ruff format --check`, `mypy .`; the example project
  (`./gradlew jar; (cd exampleProjects && ./gradlew :java-benchmarks:jmh -Pinclude=".*QuickBenchmark.*")`) and a
  look at `exampleProjects/java-benchmarks/build/reports/jmh/index.html` in a browser (the golden only compares bytes).

  - **Getting Started:** `id "com.github.mlangc.jmhreport" version "1.0.0"`; state the Gradle 8.0 requirement.
  - **Coordinates note**, near the top of Getting Started and in the News entry, so nobody looks for 1.0.0 under the

- Root `CLAUDE.md`, "Release process": keep it consistent with the README; add the `publishPlugins --validate-only`

- Checks: re-read the changed docs against the actual commands (run them where cheap); grep again for stale spots.

### 3. Extend `check.py`: test a published plugin (`--repo`), prepare `--portal`

Today the fixtures load the jar from `libs/` through `flatDir` (filled by `check.py`). Add a second way to get the
plugin into the consumer, keeping `--jar PATH` as the default:

- `--repo DIR --plugin-version V`: the fixtures apply the plugin with
  `pluginManagement { repositories { maven { url DIR } } }` and
  `plugins { id 'com.github.mlangc.jmhreport' version 'V' }`, which goes through the plugin marker artifact
  `com.github.mlangc.jmhreport:com.github.mlangc.jmhreport.gradle.plugin`, as real users do. (Gradle's convention:
  the marker's group is the plugin ID and its artifact is the ID plus `.gradle.plugin`; it is a POM-only artifact
  that depends on the implementation jar.)
- `check.py` only consumes a repository and never publishes: `--repo` and `--plugin-version` are required together,
  and `--jar` is mutually exclusive with both. The repository is produced outside of `check.py`, by a documented
  command in `blackbox-tests/CLAUDE.md`: `./gradlew publishToMavenLocal -Dmaven.repo.local=<tmp>` in the repo root,
  so `~/.m2` is never touched or shadowed.
- Design the mode switch so that `--portal` later only means "repository block = `gradlePluginPortal()`, nothing else
  changes". `--portal` itself is not implemented in this step, since there is nothing on the portal to test yet.
- All scenarios, including S10's direct reference to `JmhReportTask` and the `CC` runs, must work in both modes. The
  consumer's Gradle home / dependency cache must not make a stale 1.0.0 invisible (fresh temp dirs are used already;
  check what the Gradle user home caches for a `maven {}` repo).
- Update `blackbox-tests/CLAUDE.md` (running, layout, gotchas) and the plan reference there.
- Checks: full run in `--jar` mode (must be unchanged); full run in `--repo` mode on all five Gradle versions;
  `ruff check`, `ruff format --check`, `mypy .`; negative check that `--repo` mode really fails when the repo lacks the
  marker artifact (e.g. an empty directory), so the green run isn't vacuous.

### 4. Try `publishPlugins --validate-only`

- `./gradlew publishPlugins --validate-only` validates the publication against the Plugin Portal without uploading.
  It needs the portal credentials (`gradle.publish.key` / `gradle.publish.secret`). If the agent can't use them, the
  maintainer runs it and pastes the output; the agent investigates whatever blocks.
- Also inspect the metadata in a repo published as documented in step 3: the jar, the POM (name, description, URL,
  license, SCM) and the plugin marker artifact.
- Result: either "nothing blocks us" or a list of fixes, which are applied (and checks of steps 1 and 3 re-run).

### 5. One review round with an Opus subagent

Follow "Agentic Reviews" in the root `CLAUDE.md`: a fresh Opus subagent that reports and doesn't modify. Point the
reviewer to this plan, which states the task, the ground rules and the checks, and ask them to review everything
implemented under it so far (`git diff main...release-1.0.0`). The implementer addresses the items they agree with
directly and re-runs the affected checks. Everything else goes to the maintainer for discussion, each item with a short
reason.

### 6. Maintainer steps (not done by the agent)

1. Replace the `2026/MM/DD` placeholder in the News entry with the release date and commit it on the branch, before
   tagging.
2. Review the release branch. It is not merged yet: the release is tagged and published from the branch, and
   `main` only gets it in step 8.
3. `git tag -a 1.0.0 -m "1.0.0 release"` on the branch's head, `git push -u origin release-1.0.0`,
   `git push --tags`. The tag is `1.0.0`, without a `v`: the `mlangc/gradle-jmh-report` remote has no tags or GitHub
   releases yet (none locally either), and the original upstream repository `jzillmann/gradle-jmh-report` uses bare
   version tags (`0.1.0`, `0.4.1`, `0.4.2`, `0.5.0`, `0.6.0`, `0.6.1`, `0.6.2`, `0.6.2.1`, `0.7`, `0.8`, `0.9`; the
   later 0.9.x releases were never tagged), which matches the README's `git tag -a $releaseVersion`. `1.0.0` will be the
   first tag in this repository.
4. `./gradlew publishPlugins`.
5. Check the plugin's Plugin Portal page (ID, version, description, tags, website and VCS URL) and create a GitHub
   release from the tag with the News text.
6. Wait until the portal serves the new version. No retry logic is built for this; trying again a bit later is fine.

### 7. `--portal --plugin-version V`; double-check the published release

- Implement `--portal` on top of step 3: `gradlePluginPortal()` as the only plugin repository, no `mavenLocal()`, no
  `flatDir`. Like `--repo`, it requires `--plugin-version`, and it is mutually exclusive with `--jar` and `--repo`.
- Run `uv run check.py --portal --plugin-version 1.0.0` on all five Gradle versions. This is the real check that
  what users download works. Report the matrix. Failures are release findings for the maintainer, not something to fix
  silently.
- Update `blackbox-tests/CLAUDE.md` and the release process in the root `CLAUDE.md` / README (post-release check).
- Checks: `ruff check`, `ruff format --check`, `mypy .`; `--jar` and `--repo` modes still green.
- Commits after the tag are fine as long as they don't affect the released code. Don't commit unless you have verified
  that `git diff 1.0.0 release-1.0.0 -- src build.gradle gradle.properties` will stay empty (before committing, the
  equivalent is `git diff 1.0.0 -- src build.gradle gradle.properties`, which compares the tag with the working tree);
  or commit and amend if the verification afterwards fails.

### 8. Maintainer steps (not done by the agent)

1. Review step 7's commits (the checks were already run and reported there).
2. Merge with `git merge --ff-only release-1.0.0` on `main` (nobody commits to `main` meanwhile, so the tag stays
   on `main`'s history), `git push`, delete the release branch (local and remote) and remove the worktree.

## Open items

- **Plugin Portal and a new plugin ID.** The portal may have its own rules for a new ID or for the `com.github.*`
  namespace (ownership verification, first-publication review). They have not been verified; step 4 may surface them.
- **Credentials.** `~/.gradle/gradle.properties` is expected to contain the portal keys (`gradle.publish.key` /
  `gradle.publish.secret`), but they have never been tried. Step 4 (`publishPlugins --validate-only`) is the first
  real test; if it fails on authentication, the maintainer sorts out the keys (and that they belong to the account
  that owns the new ID) before anything else in the plan depends on them.

## Definition of done

- Agent's part (steps 1 to 5): the release branch contains the version bump, documentation changes and the
  `--repo` extension; every check above that doesn't need portal credentials is green; the review feedback is
  addressed; a short list says which steps are left for the maintainer, with the exact commands.
- Step 7: `check.py --portal --plugin-version 1.0.0` is green on all five Gradle versions (or the failures are
  reported), and the tag check holds.
- Steps 6 and 8 are the maintainer's.
